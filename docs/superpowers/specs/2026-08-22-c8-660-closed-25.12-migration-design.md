# C8-660 Closed 25.12 Migration Design

Date: 2026-08-22

## Objective

Replace the retired C8-660 closed-driver build with one maintained build based
on `chasey-dev/immortalwrt-mt798x-rebase:25.12` and Linux 6.12. The resulting
firmware must use MediaTek `mt_wifi` 7.6.7.3, HNAT, WARP/WED, and must offload
RM520N WAN traffic to both LAN and WiFi. The C8-660's current data plane is
RGMII/IPPT on `eth1`; USB/QMI remains a supported optional external data path.
The repository will not retain a 21.02 build or another legacy closed entry.

## Upstream Baseline

- Repository: `https://github.com/chasey-dev/immortalwrt-mt798x-rebase`
- Branch: `25.12`
- Initial candidate revision:
  `2d0e93b1253660ae15d195786cd7fa913d70d42a`
- Kernel: 6.12
- Wireless driver: `mt_wifi` 7.6.7.3
- Acceleration stack: `kmod-mediatek_hnat`, `kmod-warp`,
  `mtk_warp_proxy`, `MTK_WHNAT_SUPPORT`, `MTK_WARP_V2`, and
  `WED_HW_RRO_SUPPORT`

The workflow will build a fixed, reviewed commit by default instead of tracking
the branch tip silently. A manual `wrt_ref` input may select another commit for
an upgrade trial. The recorded source hash remains part of every release.

## Repository Shape

The active workflow becomes `.github/workflows/c8-660-closed.yml`. The existing
`.github/workflows/c8-660-closed-21.02.yml` is deleted. The generic closed
configuration filenames are retained but rewritten for 25.12:

- `Config/NRADIO-C8-660-CLOSED.txt`: filogic target and C8-660 device selection
- `Config/CLOSED.txt`: `mt_wifi`, HNAT, WARP/WED, and vendor LuCI selections
- `Config/GENERAL-CLOSED.txt`: packages compatible with ImmortalWrt 25.12

The retired `archive/closed-24.10/` directory is deleted so there is no second
closed build recipe. README references to 21.02, Linux 5.4, 7.6.6.1, disabled
HNAT/WARP, and the 24.10 archive are replaced by the new supported baseline.

Open `mt76` build files remain independent. Existing uncommitted Open-build and
SMS work is preserved.

## C8-660 Target Integration

The build injects the existing C8-660 hardware description into the 25.12
source tree before `make defconfig`. It preserves:

- MT7981B, MT7531, two RTL8221B PHYs, and 512 MB SPI-NAND
- BL2, u-boot-env, factory, bdinfo, FIP, and UBI partition layout
- USB 3, RM520N QMI/serial support, modem power/select GPIOs, buttons, and LEDs
- factory EEPROM and bdinfo-derived MAC addresses
- factory, sysupgrade, initramfs, manifest, BL2, and checksum artifacts

The closed image definition is separate from the Open `mt76` definition. It
must not select `kmod-mt7915e`, `kmod-mt7981-firmware`, or
`mt7981-wo-firmware`. It explicitly includes the vendor wireless and
acceleration packages required by the image.

The copied DTS receives only closed-build HNAT properties. They describe the
two-GMAC C8 topology without changing the shared Open-build DTS. Device-tree
injection is idempotent and fails if its expected source anchors are absent.

## RM520N HNAT Data Paths

The repository's normal C8-660 path is:

```text
RM520N -> RGMII/IPPT -> eth1 -> HNAT/PPE
     -> MT7531 LAN or mt_wifi/WARP/WED
```

USB carries AT/control traffic in this baseline; installing QMI packages does
not prove that QMI is the WAN data plane. The reverse RGMII/IPPT path must bind
through the same PPE flow entry, and `rxppd` is not expected when netifd reports
the GMAC root `eth1`.

If an installation explicitly switches the data plane to USB/QMI, the external
path is `qmi_wwan/wwan0 -> HNAT external hook -> Tx PPD/PPE -> rxppd in br-lan`.
`hnat-detect` reads fw4 state after WAN `ifup`, recognizes a masqueraded
external `wwan*` device, creates `rxppd` when needed, brings it up, and adds it
to `br-lan`. It must not replace the QMI WAN device or make WAN availability
depend on HNAT.

The implementation initially uses the upstream detector unchanged. Runtime
validation reads the actual netifd L3 device. If the modem exposes a different
name such as `qmimux*` or `rmnet*`, a narrow detector patch will add that class;
the design will not hard-code `wwan0` when the running device reports another
name.

Closed-driver WED is defined as the vendor chain
`mt_wifi -> mtk_warp_proxy -> WARP/WED -> HNAT/PPE`. The mt76
`wed_enable=Y` module parameter is neither required nor accepted as evidence.

## Configuration Contract

After `make defconfig`, CI requires all of the following:

```text
CONFIG_PACKAGE_kmod-mt_wifi=y
CONFIG_MTK_MT_WIFI_DRIVER_VERSION_7673=y
CONFIG_PACKAGE_kmod-conninfra=y
CONFIG_PACKAGE_kmod-mediatek_hnat=y
CONFIG_PACKAGE_kmod-warp=y
CONFIG_PACKAGE_hnat-detect=y
CONFIG_MTK_FAST_NAT_SUPPORT=y
CONFIG_MTK_WHNAT_SUPPORT=m
CONFIG_MTK_WARP_V2=y
CONFIG_WARP_CHIPSET="mt7981"
CONFIG_WARP_VERSION=2
CONFIG_WED_HW_RRO_SUPPORT=y
```

CI rejects `kmod-mt7915e`, `kmod-mt76`, driver versions 7.6.6.1/7.6.7.2,
and a missing WARP proxy. WPA3 remains enabled only if the 7.6.7.3 build and
real association tests pass; it is not silently disabled to make compilation
green.

## Build And Artifact Validation

The workflow performs these gates in order:

1. Verify the pinned source commit and the expected upstream package anchors.
2. Inject the C8 target and overlay, update feeds, and apply closed configs.
3. Run `make defconfig` and enforce the configuration contract.
4. Compile the complete firmware with failure logs and a config snapshot.
5. Inspect the manifest for vendor WiFi, HNAT, WARP, detector, QMI, modem,
   LuCI, and required C8 packages.
6. Inspect the squashfs root for `mt_wifi.ko`, `mtk_warp_proxy.ko`,
   `mtk_warp.ko`, the HNAT module, conninfra, WARP/WO firmware,
   `hnat-detect`, QMI tooling, and C8 modem files.
7. Reject mt76/mac80211 wireless driver modules in the closed rootfs.
8. Package exactly one image of each expected type and regenerate checksums.

Workflow YAML, shell syntax, configuration symbol checks, target injection
idempotency, `git diff --check`, and artifact selection receive local tests.

## Router Acceptance Tests

Compilation is necessary but is not completion. On the C8-660 router, preserve
partition backups and the last bootable image, then verify:

1. Boot without kernel oops, module load failures, or switch/PHY regressions.
2. Both WiFi bands initialize under `mt_wifi`; WPA2/WPA3 clients associate and
   obtain DHCP leases.
3. RM520N registers, the WAN zone reports `eth1` for the default RGMII/IPPT
   data plane, IPv4 NAT works, and native IPv6 behavior is unchanged.
4. HNAT hook is enabled; WARP, proxy, HNAT, and WO firmware are active.
5. If USB/QMI is deliberately selected as the WAN data plane, record the real
   netifd L3 device and require `rxppd` up in `br-lan`; do not require `rxppd`
   for the default `eth1` path.
6. Under sustained cellular-to-LAN and cellular-to-WiFi traffic, PPE `BIND`
   entries increase from the idle baseline and continue forwarding after WAN
   reconnect.
7. Compare throughput, packet loss, and per-core CPU use with HNAT enabled and
   disabled. A package/module being present does not count as offload.
8. Test cold boot, warm reboot, modem reconnect, firewall reload, WiFi restart,
   and, when testing external USB/QMI, a detector rerun without duplicate
   `rxppd` devices.
9. Disable the HNAT hook and confirm RM520N WAN still works through the software
   forwarding path.

Acceptance requires PPE binding for both LAN and WiFi traffic over the active
RM520N data plane. Optional USB/QMI data-plane support is reported separately
and is not claimed from package presence alone.

## Failure Handling And Recovery

- Source-layout drift, missing symbols, or missing modules fails CI early.
- `hnat-detect` failure logs a specific error but does not take the WAN down.
- Zero PPE binding under load, kernel warnings, or traffic regression fails
  router acceptance. A missing or detached `rxppd` is a failure only when the
  active WAN L3 device is an external USB/QMI interface.
- Router testing starts with BL2/FIP/factory/bdinfo backups and a tested TFTP
  recovery route.
- The repository does not retain a 21.02 workflow. Recovery uses saved router
  artifacts and bootloader recovery, not an active legacy CI path.

## Completion Criteria

The migration is complete only when the repository contains one closed 25.12
workflow, local validation passes, GitHub Actions produces all required
artifacts from a fixed commit, and a C8-660 proves RM520N-to-LAN and
RM520N-to-WiFi PPE binding with a working software fallback. No commit, release,
or push is created automatically from the dirty working tree.
